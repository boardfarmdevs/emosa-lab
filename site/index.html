02 / Lab manual

Choose the experiment you need

Each level answers a different question. A simulated radio adds a real Linux Wi-Fi stack to the lab; the final experiment still needs the actual pod and a client with a physical Wi-Fi interface.

Understand a result: Config committed ≠ behavior observed

A successful OVSDB transaction proves the database accepted a change. The operation engine waits for fresh State observations. Independent client evidence is another required boundary for physical acceptance. An expired deadline remains a failure even if application is observed later; a lost reply can leave commit attribution unknown.

Read the recovery contract ↗
Understand WSC scope: provisioning applies to the radio

The proposed EasyMesh 6.1 procedure configures the radio’s BSS set, including unmatched-BSS teardown. Qualify a sole-BSS radio for the first experiment, or implement the complete radio-wide request. Applying one VIF patch on a shared radio does not prove that procedure.

    04 / Path to viability

    The next proof is end to end

    The next milestone is a real EasyMesh controller discovering and onboarding the OpenSync extender as an agent represented by EMOSA, then provisioning its BSS through the adapter. Retain the controller’s agent view and independently verify the extender’s behavior.

    A useful viability verdict is bounded.

    Name the procedure, controller build, pod firmware, schema, management path, timing budget, recovery behavior, and manual interventions. Keep incompatibilities and failed runs alongside successes.
