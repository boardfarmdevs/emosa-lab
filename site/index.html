EasyMesh ⇄ OpenSync adapter

Put OpenSync pods into any EasyMesh network.

EMOSA runs next to an EasyMesh controller. Every OpenSync pod handed to it shows up at the controller as a standard EasyMesh agent. The controller configures it and sees its clients. The pod itself runs unchanged.

  • 6 pods onboarded as agents in the lab
  • 0 changes on the pods (OpenSync 6.6.1)
  • 900 s fault workload passed

    What it does today

    Verified in the lab with unchanged OpenSync 6.6.1 pods on simulated radios and a prplMesh 6.0 controller.

    Onboards every pod automatically

    Hand a pod to EMOSA and it gets its own agent. The agent's identity comes from the pod's serial, so no per-pod setup is needed and a returning pod keeps its identity.

    Applies the controller's network

    The controller sends the SSID and WPA2 passphrase in its M2 message. EMOSA writes them to the pod as one guarded change, and counts it as done only when the pod reports it running. It can optionally apply sets of fronthaul and backhaul BSSes.

    Reports the live topology

    Radios, BSSes, channel and associated clients come from the pod's own state tables. The controller hears about client joins and leaves as they happen.

    Recovers without help

    It survives an adapter restart, a lost pod connection, a lost pod backhaul and a controller restart. In a 900-second run with six pods, every fault recovered within 26 seconds.

    Not yet

    • 5 and 6 GHz radios, WPA3
    • AP and station metrics
    • Physical pods: they need EMOSA to be trusted by the pod's TLS
    • RDK controller: its configuration is accepted, bring-up still being verified

    Try it

    The lab runs on one Linux host with LXD. The OpenSync side (gateway, pods, clients) comes from opensync-lab; the EasyMesh side and EMOSA come from this repository.

    1. Build the OpenSync lab

      A gateway, three pods and their Wi-Fi clients, in one VM.

      cd opensync-lab
export MVX_VM=emosa-lab-vm MVX_HWSIM_POOL=32
./setup-vm.sh all
./deploy-mvx.sh all && ./deploy-mvx.sh mesh

    2. Add the controller and EMOSA

      A prplMesh controller, the adapter, and the controller's own UI.

      cd emosa-lab
export EMOSA_VM=emosa-lab-vm
deploy/opensync-lab/lab.sh stage
deploy/opensync-lab/lab.sh emosa
deploy/opensync-lab/lab.sh controller
deploy/opensync-lab/lab.sh ui

    3. Start the fleet and set the network

      One entry point for all pods, and the SSID the controller will hand out.

      deploy/opensync-lab/lab.sh fleet
deploy/opensync-lab/lab.sh policy emosa-mesh 'EmosaMesh2026!'

    4. Hand the pods over

      Each pod gets its agent and is configured by the controller.

      deploy/opensync-lab/lab.sh admit pod-1 pod-2 pod-3

    5. Connect a client and watch

      Open the controller UI on port 8660 of the host. Each pod appears as an agent with its network and clients. 

      deploy/opensync-lab/lab.sh client em-wc1 pod-1 emosa-mesh 'EmosaMesh2026!'
deploy/opensync-lab/lab.sh status

    6. Break things on purpose

      Fifteen minutes of faults with continuous client traffic, then a pass/fail verdict.

      deploy/opensync-lab/lab.sh workload my-first-run

    The passphrase above is a public lab value.

    Words you will meet

    EasyMesh
    The Wi-Fi Alliance standard for multi-AP home networks: one controller manages many agents.
    OpenSync
    The software on the pods. It is managed through its OVSDB database.
    Agent
    An access point that the EasyMesh controller manages. EMOSA runs one virtual agent per pod.
    IEEE 1905.1
    The message layer that EasyMesh agents and controllers talk over.
    AL MAC
    An agent's 1905 identity. EMOSA derives it from the pod's serial number.
    M1 / M2
    The WSC exchange that onboards an agent. M1 describes the radio; M2 carries the network (SSID and passphrase).
    Config / State
    OVSDB tables. Config is what is asked for; State is what the pod actually runs.
    BSS
    One Wi-Fi network on a radio. A fronthaul BSS serves clients; a backhaul BSS links extenders.
